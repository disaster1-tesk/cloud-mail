# Cloudflare production deployment

Production Worker: `cloud-mail`, from `disaster1-tesk/cloud-mail` branch `main`.
Domains: `mail.zappo.work`, `mail.happyaether.com`, `mail.pilotnet.org`,
`mail.bosslevin.net`, `mail.marleyinfo.net`, `mail.amelieorg.org`,
`mail.syeda.net`, and `mail.laurencemy.net`.

Cloudflare Workers Builds settings:

- Root directory: `mail-worker`
- Build: `pnpm test:unit && pnpm --dir ../mail-vue install --frozen-lockfile && pnpm --dir ../mail-vue build`
- Deploy: `pnpm exec wrangler d1 migrations apply db --remote --config wrangler.production.toml && pnpm exec wrangler deploy --config wrangler.production.toml`
- Preview builds: disabled (feature branches must not deploy to production)
- Node.js: `24.14.1`; pnpm: `10.33.0`
- Reuse the existing `cloud-mail build token` in Cloudflare.

Push or merge changes to `main` to deploy. Cloudflare's build log is the source
of deployment status. The legacy GitHub Actions deployment is manual-only to
avoid two deployment systems publishing the same Worker.

`wrangler.production.toml` binds the existing D1 database and preserves runtime
variables and secrets managed in Cloudflare. It intentionally leaves custom
domains managed in the dashboard. `src/adapter/d1-kv.js` preserves the production
`kv_store` format for cached settings, sessions and attachments; do not remove it
unless those records have been migrated to another storage backend.

Production D1 changes belong in new numbered files under
`mail-worker/migrations/production`. Applied migrations must not be edited.
Migration `0001_forwarding.sql` upgrades the existing v3.3 database. It is not a
fresh installation schema. Migration `0002_forwarding_per_user.sql` adds the
`user_forward` table used by the per-user forwarding rework; the `account_forward`
table from `0001` is no longer referenced by code and is left in place. Changes to cached settings also require refreshing
the `setting:` cache through the application initialization/settings flow.
Migration `0003_ui_theme.sql` adds the `setting.ui_theme` column required by the
latest interface settings.

## Rollback

In Cloudflare, open Worker **Deployments**, select a known good version and
choose rollback. Alternatively use `pnpm exec wrangler rollback <version-id>
--config wrangler.production.toml` from `mail-worker`.

The pre-update version on 2026-11-11 was
`f2fb60e8-61c5-435d-815f-ed001090ad99`. The forwarding schema additions are
compatible with that version; leave the database intact when rolling back code.
Revert the corresponding Git commit on `main` to prevent a subsequent build
from redeploying the unwanted version.

## Cloudflare Email Sending

The production configuration binds `send_email` as **`email`**. Both ordinary
outbound mail and user forwarding prefer this binding over Resend. Binding it
does not onboard sending domains or verify recipients by itself.

Before merging a change that enables the binding:

1. In the Cloudflare account, open **Compute → Email Service → Email Sending**.
   Sending to arbitrary recipients requires **Workers Paid**. As checked on
   2026-11-15, Workers Paid starts at USD 5 per account/month; Email Sending
   includes 3,000 messages per month and charges USD 0.35 per additional 1,000.
   Other resource overages are separate. The account owner completes purchase.
2. Use **Onboard Domain** for each of `bosslevin.net`, `zappo.work`,
   `happyaether.com`, `pilotnet.org`, `marleyinfo.net`, `amelieorg.org`,
   `syeda.net`, and `laurencemy.net`. Review and apply the actual DNS entries
   generated by Cloudflare. Retain existing inbound Email Routing records.
3. Verify all eight domains' sending DNS status, including SPF and DKIM, and
   review the account's current daily sending limit before enabling production
   sending. A domain being active in DNS or Email Routing is not confirmation
   that it is onboarded for Email Sending.
4. Merge the fork PR into `main`, then verify the Workers Builds result,
   deployed commit/version, and the **`email`** send-email binding on
   `cloud-mail`. Feature branches do not deploy production.
5. Run the user-forwarding acceptance checks with real mailbox receipts:
   verification code, external mail with attachment and inline image, Reply-To
   reply, another owned domain, on-site mail, loop prevention, and failure
   disable/re-enable. Unit tests and dry runs do not establish delivery.

### DNS review checklist

Cloudflare generates these sending records; obtain complete values and MX
priorities from the actual onboarding screen instead of inventing a DKIM key.

| Type | Name relative to each domain | Value / source |
| --- | --- | --- |
| MX | `cf-bounce` | Cloudflare-generated bounce routing servers and priorities |
| TXT | `cf-bounce` | Sending SPF generated by Cloudflare |
| TXT | `cf-bounce._domainkey` | Domain's generated DKIM public key |
| TXT | `_dmarc` | Review the proposed policy against any existing policy |

Do not replace the root domain's inbound MX or add duplicate SPF/DMARC records.
Email Routing DKIM and Email Sending DKIM are separate configurations.

### Forwarding verification considerations

- Forwarding targets are shared by all mailboxes owned by a user. The channel
  selector checks whether `env.email` exists, not whether a sender domain is
  onboarded. Sends from an unverified domain can fail and increment the shared
  target's failure counter; ten consecutive failures disable that target.
  Onboard all sending domains before enabling this binding.
- Changing a Resend token has no effect while `env.email` is present. Use a
  separately agreed, narrowly scoped Cloudflare failure test, then restore it
  and verify re-enable plus delivery. Do not deliberately break all domains'
  DNS or account-wide sending just to exercise the counter.
- The user's Postbox verification code and Cloudflare's verified destination
  addresses are separate. The latter are not a substitute for self-service
  sending to arbitrary recipients.
- Cloudflare API acceptance is not sufficient evidence of Gmail receipt.
  Inspect Gmail spam, authentication results, attachments, inline image, and
  original headers (`Reply-To`, `X-CloudMail-Forwarded: 1`).

For a sending rollback, revert the binding change through a new fork PR and
redeploy, or roll back to the previously recorded Worker version. Leave D1
migrations and inbound routing intact; without another sending provider,
user forwarding will again be unavailable. DNS onboarding and Workers Paid
are separate account changes, not automatically reverted with Git.
